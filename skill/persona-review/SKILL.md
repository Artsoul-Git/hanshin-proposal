# persona-review スキル — ペルソナ品質部

## 役割定義

**ターゲット読者になりきって成果物を読み、「伝わらない」を先に見つける。**

- 作り手（専門スキル）の「言いたいこと」ではなく、読み手の「わかること」を基準に評価する
- 専門知識のある書き手バイアスを排除して読む
- 改善案なしの指摘はしない。必ず「こう変えると伝わる」をセットで出す

---

## 起動条件

### 自動起動（fact-check合格後）
fact-check が「合格」判定を出したクライアント向け成果物に対して、Kaiが自動的に本スキルを呼び出す。

### 手動呼び出し
```
/persona-review [ファイルパス]
例：/persona-review 05_クライアント案件/まる/提案書v11.html
```
または「このドキュメントをペルソナ視点でチェックして」と伝える。

---

## Step 1：ペルソナの特定

**チェック前に必ず「誰に向けて書いたか」を確認する。**

### ペルソナ情報の取得元（優先順）

1. **提案書の場合** → `Knowledge/` のスターターパック・ヒアリング記録から取得
   - ITリテラシーレベル（1〜5のどこか）
   - 役職・年齢層・業種
   - 過去のIT導入経験（成功/失敗）

2. **Brain記事の場合** → 記事冒頭または`Knowledge/`の記事設定ファイルから取得
   - ターゲット読者像
   - 悩み・課題
   - 記事を読む動機

3. **マニュアル・ガイドの場合** → 冒頭の「対象読者」セクション、またはヒアリング記録

4. **情報がない場合** → Kaiが以下を明示して実行し、完了後に上村に確認を求める：
   ```
   ペルソナ情報が見つかりません。以下の想定で進めます：
   想定ペルソナ：[業種・役職・ITリテラシーLv・主な懸念]
   → 違う場合は修正してください。
   ```

### ペルソナシートの作成（チェック開始前）

```
【使用ペルソナ】
名前（仮）：[ペルソナ名 例：田中さん]
属性：[役職・年代・業種]
ITリテラシー：Lv[1-5]（1=スマホのみ / 3=PC日常使用 / 5=システム担当者）
主な懸念：[例：コストが高そう / うちの現場で使えるか不安]
読む動機：[例：経営者から渡された / 自分でAI導入を検討している]
読む状況：[例：会議前に10分で目を通す / じっくり比較検討中]
```

## チェック4軸

### P1. リテラシー適合チェック
ペルソナのITリテラシーレベルで「読める」か検証する。

**Lv別基準：**
| Lv | 基準 |
|----|------|
| 1〜2 | スマホ操作は普通。PC・クラウド・API等は知らない前提。カタカナ用語は全て説明必要 |
| 3 | PCの日常利用は可能。Excelは使える。クラウドの概念はある。専門システムは説明必要 |
| 4〜5 | IT一般知識はある。業種特有の専門用語（医療・福祉等）のみ説明必要 |

**検出対象：**
- 説明なしで使われているIT・AI用語（API、SaaS、GAS、スプレッドシート等）
- ペルソナのLvを超えた前提知識が必要な説明
- 文章の複雑さ（1文が長すぎる・主語が遠い・受け身多用）

```
検証アクション：
  適合  → ✅
  用語過多・説明不足 → ⚠️ [用語名]：[補足説明案] を提示して差し戻し
```

### P2. 専門用語チェック
説明なしで登場する専門用語・略語・業界慣用語を洗い出す。

**検出対象：**
- IT用語（API、GAS、GWS、CSV、クラウド、SaaS等）
- AI用語（プロンプト、LLM、トークン、ファインチューニング等）
- 業種専門用語（障害福祉：個別支援計画、国保連 / 医療：SOAP、カルテ等）
- アートソウル社内用語（ライモBiz等 → 初出で説明を添えているか）

```
検証アクション：
  初出で説明あり → ✅
  説明なし → ⚠️ 「[用語]（[説明]）」の形式で補足案を提示
```

### P3. 感情シミュレーション
ペルソナとして成果物を通読し、感情・疑問・離脱ポイントを予測する。

**シミュレーションの観点：**

```
読み始め（冒頭）：
  → 「これは自分に関係ある話か？」と思えるか
  → 冒頭で離脱する理由があるか

中盤（課題・解決策）：
  → 「本当にうちで使えるのか？」という疑問は解消されているか
  → 「難しそう」「リスクが大きそう」と感じるポイントはどこか
  → 不安・懐疑心が高まる表現はあるか

終盤（料金・CTA）：
  → 「高い」「わからない」「次に何をすればいいかわからない」という反応はないか
  → 読み終えて「で、どうすればいいの？」と思わないか
```

**出力形式：**
```
感情シミュレーション結果：
  ✅ 冒頭：共感から入っており離脱リスク低い
  ⚠️ p.3「API連携」：ペルソナLv2では意味不明。「外部システムとの自動連携」に変更推奨
  ⚠️ 料金セクション：比較対象がなく「高い」印象。「現在の残業代と比較すると…」の一文追加推奨
  ✅ CTA：次のアクションが明確
```

### P4. 行動促進チェック
読み終えた後に「何をすべきか」が明確に伝わるか検証する。

**確認内容：**
- 最終CTAが具体的なアクションになっているか（「お問い合わせください」→「まず無料相談を申し込む」）
- 読後に必要な情報（連絡先・次のステップ）がすぐ見つかるか
- 「もっと知りたい」と思った時の行き先があるか
- Brain記事の場合：今すぐできる「最初の一手」が明示されているか

```
検証アクション：
  明確  → ✅
  曖昧・不足 → ⚠️ 改善案を提示
```

## 差し戻しフロー（無限ループ防止）

fact-checkと同じ3段階ルールを適用する（`rules/check-pipeline-rules.md` 参照）。

```
【1回目差し戻し（CHECK_COUNT継続）】
  → P1〜P4の問題箇所を番号付きで明示
  → 各問題に「改善案」を必ず添える（指摘だけしない）
  → 担当スキルで修正後、/persona-review で再チェック
  → 再チェックは指摘箇所のみ確認（全文再走査しない）

【2回目差し戻し】
  → Kaiが直接修正を試みる
  → 修正後、自ら再チェック
  → 改善できた場合 → 合格
  → 改善できない場合（ペルソナ情報不足・設計上の問題）→ エスカレーション

【エスカレーション】
  → ループ停止
  → 上村へ：「[成果物名] でペルソナ視点の問題が解決できません。
     問題：[具体的に]
     解決に必要なこと：[追加情報 / 設計の変更 / オーナー判断]」
```

## チェック完了後：判定と報告

### 報告フォーマット（合格時）

```
【persona-review 完了レポート】
対象：[ファイル名]
実行日時：[YYYY-MM-DD HH:MM]
使用ペルソナ：[ペルソナ名（属性・Lv）]

P1. リテラシー適合：✅ Lv[n]向けとして適切
P2. 専門用語：✅ [n]件確認 / 補足追加[n]件
P3. 感情シミュレーション：✅ 離脱リスク低 / ⚠️ [修正した内容]
P4. 行動促進：✅ CTAが明確

判定：合格
→ Kai最終確認へ進みます
```

### 報告フォーマット（差し戻し時）

```
【persona-review 差し戻しレポート】
対象：[ファイル名]
実行日時：[YYYY-MM-DD HH:MM]
使用ペルソナ：[ペルソナ名（属性・Lv）]

要改善箇所：
  [1] P1 / 箇所：「GASで自動化」/ 問題：Lv2には意味不明
      改善案：「Google スプレッドシートの自動化機能で」に変更
  [2] P3 / 箇所：料金セクション / 問題：比較なしで金額が高く見える
      改善案：「現在の残業代（月XX時間×時給）と比較すると…」を追加
  ...

修正後、/persona-review で再チェックをお願いします。
```
