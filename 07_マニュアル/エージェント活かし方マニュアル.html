第1章　エージェントとは何か — Kaiとの違い

エージェントは「特定の仕事だけを集中してこなす専門家」です。Kai（メインAI）とはまったく別のプロセスで動き、同時並列実行ができます。

Kai vs エージェント — 基本の違い

比較項目Kai（メイン）エージェント
役割司令官・調整役・最終判断特定タスクの専門実行者
知識CLAUDE.md・memory・Knowledge全体自分のSKILL.mdに書かれた指示のみ
同時実行1つ（会話の流れに従う）複数を同時に動かせる（並列化）
会話履歴あり（セッション全体を覚えている）なし（毎回ゼロから起動）
ツール制限制限なしSKILL.mdで明示したツールのみ
コスト1回分のトークンエージェント数分のトークン（並列なら合算）

なぜエージェントを使うのか

  • スピード：6つの発信物を1体ずつ順番に作ると30分かかるところを、6体並列なら5分で終わる
  • 専門性：「Xスレッドの書き方だけ」に特化した指示を渡せるため、品質が上がる
  • トークン節約：メイン会話にすべての中間成果物を流さず、ファイルで受け渡しする
  • 再現性：SKILL.mdに書かれた手順が常に同じように実行される
コンテキストの引き継ぎ方 エージェントは会話履歴を持ちません。Kaiが「outdir（出力フォルダパス）」や「研究ノートファイルパス」などを引数で渡すことで、エージェント間のバトンがつながります。ファイルベースの受け渡しがKaiエコシステムの基本設計です。

エージェントファイルはどこにある？

場所対象エージェント詳細ガイド
.claude/agents/*.md content-burst チーム（7体）・deck-sprint チーム（4体） エージェントガイド（スキル用）
08_アプリ開発事業部/agents/*.md ARCH + 開発専門エージェント（8体） エージェントガイド（開発部）

第3章　「Kai一人か」「チームか」を判断する

すべての作業でエージェントチームを使う必要はありません。判断基準を理解して、状況に合った選択をしましょう。

判断フローチャート

Q1. 複数の異なるアウトプット形式が必要か？
YES → エージェントチームを検討する
NO → 次の質問へ
Q2. アウトプットが3,000字を超える大規模な成果物か？
YES → エージェントに委任する（専門的な大量生成に強い）
NO → 次の質問へ
Q3. Web検索が5回以上必要なリサーチ作業か？
YES → cb-scout / ds-scout を使う（制限付きで集中リサーチ）
NO → 次の質問へ
Q4. アプリ・ツール開発（コーディング）が必要か？
YES → ARCH チームに委任する
NO → Kai一人で十分。そのまま依頼する

第5章　deck-sprint チーム詳細（4体）

deck-sprint は「調査→スライド→会議準備を5分で揃える」高速資料作成チームです。

チームフロー

各エージェント詳細

ds-scout
リサーチ専門（直列先行）
WebSearch 最大3回（厳守）。速度優先。信頼性の高いソースのみ選定し research-notes.md に整理。
ds-analyst
構造化レポート
5,000〜8,000字・7〜9章。事実→解釈→示唆の3層構造で深掘り。report.md として出力。
ds-deck
HTMLスライド（Edit差し替え方式）
Write禁止・Editのみ使用。slide-base.html をコピーしたテンプレートに、タイトルとスライド群を差し替えて完成。毎回ゼロ生成しないため高速。
ds-chair
報告MTGアジェンダ
想定質問5問以上（うち1〜2問は懐疑的・批判的視点）。タイムライン・進行メモ・事前配布物リスト付き。

ds-deck の仕組み（Edit差し替え方式）

なぜ Write を使わないのか スライドのCSS/JSは数百行あります。毎回 Write で全量生成するとトークンを大量消費し、ミスも増えます。ds-deck はベーステンプレートをコピー後、__KAI_TITLE__ と <!-- [KAI_SLIDES_START] -->〜<!-- [KAI_SLIDES_END] --> の2箇所だけ Edit で差し替えます。変更範囲が最小限なため、5分以内を実現しています。
詳細ガイド 各エージェントの詳細仕様・スライドCSSクラス一覧・MTG活用法は deck-sprint 徹底使い倒しガイド および エージェントガイド（スキル用） を参照してください。

第6章　ARCH 開発エージェント群（8体）

ARCH は「アプリ・ツール開発の統括」を担うオーケストレーターです。8体の専門開発エージェントを束ねて、要件定義から納品まで一貫して対応します。

ARCH の位置づけ

ARCH はメインKaiから委託を受け、開発案件の全体を指揮します。ARCH 自身は「何をどの順番でどの専門エージェントに任せるか」を決め、成果物の品質を確認してKaiに返却します。

第7章　エージェントにコンテキストを渡す技術

エージェントは「セッション記憶なし」で動きます。必要な情報をすべてプロンプトかファイルで渡すのが鉄則です。

コンテキストの渡し方3パターン

引数で渡す（最も基本）

Kaiがエージェントを呼ぶとき、出力フォルダパスや入力ファイルパスを引数として渡します。

# KaiがAgent呼び出し時に渡す引数の例
outdir = "08_アプリ開発事業部/outputs/content-burst/run_20260515_1030"
research_notes = f"{outdir}/research-notes.md"

# cb-inkのpromptに含める
prompt = f"""research-notes.md を読んでHTMLレポートを生成して。
入力: {research_notes}
出力: {outdir}/report.html"""

ファイル経由で渡す（エージェント間バトン）

cb-scout / ds-scout が生成した research-notes.md を他のエージェントが読み込みます。エージェント間の唯一の接点がこのファイルです。

後続エージェントのプロンプトには「まず research-notes.md を Read してから書け」と明記します。

Knowledge ファイルを渡す（クライアント文脈の注入）

クライアント向けコンテンツを作る場合、Knowledge フォルダ内のファイルパスをエージェントプロンプトに含めます。エージェントは自分でファイルを Read してコンテキストを把握します。

prompt += f"\nクライアント情報: Knowledge/00_Kaiスターターパック.md を Read すること"
注意Knowledge フォルダは実データです。エージェントに渡す場合も「参照のみ」「外部転記禁止」の制約は守られます。

コンテキストが多すぎる場合の対処

エージェントに渡すコンテキストが大きすぎるとトークン超過でエラーになります。

対処法説明
要約ファイルを先に作る全文ではなく、重要点を抽出した要約ファイルを渡す
ページ指定で Read させる「offset: 100, limit: 50」でファイルの必要部分だけを参照させる
エージェントを分割する1エージェントの責務を絞り、渡す情報を最小化する

第8章　並列実行 vs 直列実行の設計思想

Kaiエコシステムが採用している「直列先行→並列実行」パターンは、速度と品質を両立させるための設計です。

なぜ「リサーチだけ先に直列」なのか

content-burst も deck-sprint も、必ず「スカウト（リサーチ）エージェントを1体先行させてから、残り全員を並列に動かす」という設計になっています。

パターンメリットデメリット
全員並列（リサーチ共有なし）最速各エージェントがバラバラに検索して内容がバラバラになる。重複作業も多い。
全員直列（順番に一人ずつ）情報共有は完璧一番遅い。全体で1〜2時間かかることも。
直列先行→並列実行（Kaiの設計）リサーチは共有できて品質が揃う。執筆は並列で高速。リサーチフェーズは直列なので若干待つ。

新しいスキルを設計するときの並列設計指針

  1. 情報収集（必ず直列）：WebSearch/WebFetch を含むエージェントを1体先行させる
  2. 加工・生成（並列OK）：完成した research-notes.md を読むだけのエージェントは全員同時に動かしてよい
  3. 統合・品質確認（直列）：複数の成果物をまとめてレビューする場合は並列後に直列で確認する

並列実行のKai呼び出し方法

1メッセージで複数Agent呼び出し = 並列実行 Kaiが1回のレスポンスの中で複数の Agent() 呼び出しを行うと、それらは並列に実行されます。直列にしたい場合は、前のAgent完了を待ってから次のAgent呼び出しを別メッセージで行います。 
# 並列実行（1メッセージ内に複数Agent呼び出し）
Agent(cb-ink, prompt=..., outdir=...)   ← 同時に起動
Agent(cb-pen, prompt=..., outdir=...)   ← 同時に起動
Agent(cb-spark, prompt=..., outdir=...) ← 同時に起動

# 直列実行（前のAgentが完了してから次を呼ぶ）
result_scout = Agent(cb-scout, prompt=...) ← 完了待ち
# cb-scoutが終わってから↓を呼ぶ
Agent(cb-ink, prompt=f"research-notes読んで: {outdir}/research-notes.md")

第9章　新しいエージェントを設計・追加する

既存エージェントで対応できない専門業務が出てきたら、新しいエージェントを追加します。設計から追加まで15〜30分で完了します。

設計の5ステップ

責務を1行で定義する

「このエージェントは〇〇だけをする」と1文で言えること。複数の責務を持たせない。

例：「ブログ記事HTMLを生成する」「想定質問リストを作成する」

入力・出力・ツール制限を決める

項目決めること
入力受け取るファイルパスや引数（例: research-notes.md のパス）
出力生成するファイル名と形式（例: outdir/blog-post.html）
ツール使ってよいツールを明示（WebSearch 不可・Read/Write/Edit のみ、等）

SKILL.md ファイルを書く

フロントマターに name・description・tools（許可ツールのリスト）を書く。本文に「何を・どう・どの形式で」を箇条書きで明記する。

---
name: cb-spark
description: cb-scoutのリサーチ結果をもとにXスレッドを生成する
tools: Read, Write
---

## 責務
research-notes.md を読んでXスレッド投稿（6〜9投稿）を生成する。

## 出力
- ファイル: {outdir}/x-thread.md
- 各投稿: 140字以内、番号付き（1/7〜7/7）
...

保存場所を決めて配置する

エージェントの種類保存場所
スキル（/content-burst等）から呼ぶ.claude/agents/〈名前〉.md
アプリ開発部（ARCH系）から呼ぶ08_アプリ開発事業部/agents/〈名前〉.md

SKILL.md のフローに組み込む（スキルから呼ぶ場合）

既存スキルに新エージェントを追加する場合は、対象スキルの SKILL.md の「フェーズC」または「ステップ5」部分に Agent 呼び出しを追加します。並列エージェント群に追加するだけで自動的に並列実行されます。

命名規則

チームプレフィックス例
content-burstcb-cb-scout, cb-ink, cb-spark
deck-sprintds-ds-scout, ds-analyst, ds-deck
ARCH開発チーム大文字英語SPEC, WIRE, SHIELD
新しいスキル〈スキル略称〉-mkt-scout, pr-writer 等
エージェントガイドの更新を忘れずに 新エージェントを追加したら、対応する エージェントガイド.html に仕様カードを追記してください。総合マニュアルはエージェントガイドへのリンクで参照するため、個別更新は不要です。

第10章　よくある失敗パターンと対処法

エージェントを使い始めたときに陥りやすい失敗と、その対処法をまとめました。

失敗パターン一覧

失敗① 「リサーチなしで全員並列」

cb-scout / ds-scout を省いて、いきなり全エージェントを並列起動した。

結果：各エージェントがバラバラにWeb検索し、互いに違うデータを参照した成果物が出来上がった。

対処：必ずスカウトエージェントを先行させ、research-notes.md ができてから並列フェーズを開始する。

失敗② 「出力フォルダパスを渡さなかった」

エージェントへの引数に outdir を含め忘れた。

結果：エージェントが勝手なパスにファイルを保存し、後続エージェントがファイルを見つけられなかった。

対処：Kaiがエージェントを呼ぶ前に outdir を確定させ、すべてのエージェントのプロンプトに統一パスを含める。

失敗③ 「エージェントに会話文脈を期待した」

「さっき話した内容をベースに」とエージェントに渡した。

結果：エージェントは会話履歴を持たないため、何もベースにせずデフォルト内容を生成した。

対処：必要な文脈はすべてプロンプトかファイルに書き下ろして渡す。「さっきの話」はKaiがまとめてファイルに保存してからエージェントに渡す。

失敗④ 「ds-deck に Write を使わせた」

ds-deck のプロンプトから Write の制限を外した or Write を使う指示をした。

結果：ds-deck が CSS/JS を全量再生成しようとして、テンプレートのスタイルが崩れた。

対処：ds-deck は「Edit のみ」「Write 禁止」を必ず維持する。スタイル変更はテンプレートファイル（slide-base.html）を直接編集して対応する。

失敗⑤ 「Knowledge データをエージェント経由で外部に出した」

Knowledge フォルダの実データをエージェントに渡し、そのデータが成果物に直接転記された。

結果：クライアントの実情報がHTML成果物に含まれた状態で公開リスクが発生した。

対処：エージェントへの Knowledge 渡しは「参照のみ」に限定する。成果物に書くのは一般論・匿名化情報のみ。

迷ったときのチェックリスト
  • □ スカウトエージェントを先行させているか？
  • □ outdir をすべてのエージェントに渡しているか？
  • □ エージェントに会話文脈を「ファイル or プロンプト」で明示しているか？
  • □ ds-deck に Write 禁止の制約があるか？
  • □ Knowledge データの扱いが参照のみになっているか？
