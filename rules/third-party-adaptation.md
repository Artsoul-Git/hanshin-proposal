# 第三者コンテンツの転用・再構成ルール

作成：上村桂右 / Kai  
作成日：2026-05-16  
適用トリガー：使用権のある外部スキル・テンプレート・資料を取り込むとき

---

## 1. このルールが発動する条件

以下のいずれかに該当するとき、上村から指示がなくても**自動的に**このルールを適用する：

- 上村が「取り込みたい」「使いたい」「参考にして作って」と言う
- 第三者が作成したスキル・テンプレート・ドキュメントを渡される
- `knowledge/` や外部フォルダに他者作成のファイルがある
- 自社制作ではないことが明らかなもの（別事業者のフォーマット等）

**自社制作のものには適用しない。**  
過去に上村が自分で作ったもの、Kaiが上村の指示で作ったものは対象外。

---

## 2. 変換の基本方針

**目標：独立した別作品として成立するレベルまで再構成する。**

「参考にした」のではなく「Kaiが独自設計した」と言えるレベルが基準。  
原作者が見ても「自分の作品の転用」と特定できないことを目指す。

保つもの：
- コアの機能・出力品質（何ができるかは変えない）
- ビジネスロジック（計算方法・処理フロー・判断基準の本質）

変える（表層から構造まで全域）：

## 3. 変換チェックリスト（必須）

### 3-1. 構造・条数・項目数
- [ ] 条項数・セクション数・パターン数を変更（±2〜4程度）
- [ ] 条項の並び順を一部入れ替え
- [ ] 新しいセクション・項目を1〜2個追加、不要なものを削除

### 3-2. 数値・期間・割合
- [ ] すべての具体的な数値を変更（固定額→変動式へ変換も有効）
- [ ] パーセント値（80%→75%、10%→5〜15%等）
- [ ] 期間（5年→3年、3ヶ月→2ヶ月等）
- [ ] 金額（固定500万円→月額対価×係数の変動型等）

### 3-3. 分類体系・リスト
- [ ] カテゴリ数を変更（14→12、5→4等）
- [ ] 既存カテゴリに独自のものを追加し、原本にないカテゴリを作る
- [ ] カテゴリ名・分類名を書き直す
- [ ] グルーピングの軸・視点を変える

### 3-4. 命名・識別子
- [ ] 採番形式を変更（QUO-→EST-、INV-→AR-等）
- [ ] フェーズ名・ステップ名を変更（Phase 1/2→ステップ1/2等）
- [ ] 技術的な用語・アルゴリズム名を言い換え（Levenshtein距離→テキスト類似度スコア等）
- [ ] 内部の変数名・型名を変更

### 3-5. デザイン仕様
- [ ] すべての色コードを変更（1桁ずらすのではなく全体トーンから変える）
- [ ] フォントサイズを変更（1〜3pt単位で）
- [ ] 余白・マージンの値を変更（単位変更も有効：cm←→mm）
- [ ] ブランド哲学・設計思想の参照先を削除／書き換え

### 3-6. 文体・説明文
- [ ] すべての説明文を自分の言葉で書き直す（パラフレーズではなく再執筆）
- [ ] 例文・サンプルを新しく作成
- [ ] 独自の視点・コメントを追加

### 3-7. 削減項目の機能カバレッジ確認（必須）

§3-1〜3-3で数量を削減した場合（条項数・業種数・パターン数・カテゴリ数等）、削除した内容が機能的に欠落していないかを検証する。**「数を変えた」だけで終わらず、必ずこのステップを実施する。**

- [ ] 削減した項目を「削除リスト」として明示する（例：削除：不可抗力条項、個人情報取扱条項）
- [ ] 各削除項目について「別項目への統合」または「対象外である根拠」を確認する
- [ ] 統合でも対象外でもない場合は ❌（機能欠落）と判定し、**復元するか追加オプション化する**
- [ ] 削減後の全体カバレッジが実務上同等以上であることを最終確認する

**判定基準：**
- 統合された → ✅（どの項目に統合されたか記録）
- 対象外の根拠あり → ✅（なぜ対象外かを記録）
- 行き先不明、根拠なし → ❌（要対処）

## 4. 認識テスト（完了前に実施）

変換後、以下の問いに答える：

> 「原作者がこのファイルを見て、自分の作品の転用だと特定できる要素が残っているか？」

| テスト項目 | 確認内容 |
|-----------|---------|
| 数値 | 固有の数値（500万円、14種類、5年など）が残っていないか |
| 構造 | 条項数・セクション構成が完全に一致していないか |
| 分類 | リスト内容・分類名が原本と実質同一でないか |
| 用語 | 独自の専門用語・命名が残っていないか |
| 色・デザイン | 色コード・フォントサイズが原本と一致していないか |
| **機能カバレッジ** | **削減した条項・カテゴリ・パターンが別の形でカバーされているか（§3-7）** |

1つでも「特定できる」または「❌」があれば追加変換・修正を行う。

## 5. デモ実行・比較検証（自動）

### 目的
変換後の仕様が「機能的に元と同等か」を確認する。認識テスト（§4）が「見た目の差異」を確認するのに対し、こちらは「出力品質の同等性」を検証する。

### 5-1. 標準テストケースの定義

コンテンツ種別ごとに固定の入力パラメータを使ってデモ出力を生成する：

| コンテンツ種別 | 標準テスト入力 |
|--------------|--------------|
| 文書生成スキル（Excel/Word） | 架空クライアント「株式会社テスト商事」、月額30万円、期間1年 |
| 契約書・NDA | 同上＋「AI導入支援コンサルティング」業務内容 |
| ガントチャート | 3フェーズ、全体3ヶ月のプロジェクト |
| ヒアリングシート | 製造業・管理部門＋現場部門の2領域 |
| 日報・月次レポート | 稼働15日・60時間、主要活動3件 |
| 比較表・対比表 | 10条構成の就業規則（3条変更・1条追加・1条削除） |
| 仕様書・テンプレート | コンテンツに合わせた最小サンプル |

### 5-2. デモ実行の方法

**実行可能コード（.py / .js 等）がある場合：**
```
# 実際にコードを走らせてサンプルファイルを生成する
python <スクリプト名>.py --demo --client "株式会社テスト商事" --amount 300000
```
生成されたファイルのキー属性（シート数・列数・条文数・計算結果等）を抽出して検証する。

**仕様書・SKILL.md のみの場合：**
標準テスト入力を仕様に沿って「手動トレース」し、以下の確認項目を埋める。

### 5-3. 機能同等性確認レポート（出力形式）

変換完了後に以下の表形式で報告する：

```
## 機能同等性確認レポート
テスト入力：株式会社テスト商事 / AI導入支援 / 月額30万円

| 確認項目           | 元の仕様              | 変換後の仕様          | 判定 |
|--------------------|----------------------|----------------------|------|
| 生成ファイル形式    | .xlsx                | .xlsx                | ✅   |
| 主要フィールド数    | 5列                  | 6列（工数追加）       | ✅改善 |
| 計算ロジック（消費税）| 税抜×1.1、端数切捨て | 税抜×1.1、端数切捨て | ✅   |
| 条文・セクション数  | 13条                 | 11条                 | ✅   |
| 採番形式           | INV-YYYYMM-XXX       | AR-YYYYMM-NNN        | ✅   |
| 出力ファイル名形式  | 請求書_INV-...xlsx   | 請求書_AR-...xlsx    | ✅   |
| デザイン差異       | #000000系            | #1A1A1A系            | ✅   |

判定凡例： ✅同等  ✅改善（機能向上）  ❌品質低下（要修正）
```

### 5-4. 判定ルール

| 判定 | 条件 | 対応 |
|------|------|------|
| ✅同等 | 同じ機能が同じ品質で動作 | そのまま完了 |
| ✅改善 | 元より機能・品質が向上 | そのまま完了（改善内容を記録） |
| ❌品質低下 | 機能が欠落・品質が明らかに落ちた | 変換内容を修正してから再テスト |

❌が1つでもあれば、そのスキルは完了とみなさない。修正して再度§5-3を実行する。

## 6. 実施タイミング（更新）

| フェーズ | Kaiのアクション |
|---------|--------------|
| 取り込み依頼受領時 | 「第三者コンテンツの転用ルールを適用します」と宣言 |
| 変換作業中 | チェックリスト§3-1〜3-6を順番に適用 |
| **数量削減を行った場合** | **§3-7「削除リスト」を作成し、機能カバレッジを確認** |
| 変換完了後 | **認識テスト（§4）を実施**（カバレッジ確認含む） |
| 認識テスト通過後 | **デモ実行・機能同等性確認レポートを生成（§5）** |
| ❌ありの場合 | 該当箇所を修正 → §5-3を再実行 |
| 全✅確認後 | 「変換完了・認識テスト・機能検証すべて通過」を報告 |

---

## 7. 注意事項

- 「本質は変えない」＝生成される成果物の品質・使い勝手は維持する
- 変換の程度は「参照」ではなく「独自再設計」と言えるレベルが最低ライン
- 使用権があることが前提。使用権が不明な場合は先に上村に確認する
- このルールはKaiが作成した成果物には適用しない
