## 1. 現状診断

### できていること
- Kaiと上村の協業基盤（憲法・スキル・memory）が整った
- 業種特化の提案実績（障害福祉・就労支援）が蓄積中
- 「オペレーション改善が先」という差別化哲学がある
- Brain記事・セミナーによるスケーラブル収益の萌芽がある

### 構造的な問題
| 問題 | 現状の影響 |
|------|----------|
| 上村がすべての判断点に存在する | スループット（処理できる案件数）がキャパシティに縛られる |
| Knowledgeへの情報投入が場当たり的 | Kaiが自律行動できる質のインプットが不足 |
| Kaiの修正→学習ループがない | 同じ修正を繰り返す。Kaiが育たない |
| 案件全体の鳥瞰図がない | 「今どの案件がどの状態か」が会話コンテキストにしかない |

## 2. 目標状態：Kai 90% / 上村 10% モデル

```
【今】
上村：依頼→判断→確認→判断→確認→公開承認
Kai：受け取り→実行→受け取り→実行

【目標】
上村：依頼（方向性だけ）→ブリーフィング承認→最終確認
Kai：解釈→補完→設計→実行→自己検証→提示
```

上村が担うべき本質的な役割：
- クライアントとの関係構築・信頼維持
- 事業の方向性判断（どの案件を取る、何を優先する）
- 最終成果物の承認（品質保証の最終責任）

それ以外はKaiが処理できる状態にする。

## 3. 改革の5本柱

### 柱1：ナレッジ標準化パイプライン

**問題：** Knowledgeフォルダの中身が案件によってバラバラ。Kaiが「この情報があれば動ける」が定義されていない。

**解決策：**
- 案件開始時に「Kaiスターターパック」テンプレートを使用
- 上村が毎回ヒアリング後にこのフォーマットで記録する（口頭メモ可→Kaiが整形）
- Kaiが「これだけあれば提案書が作れる」を明示する品質基準を定義

```
Kaiスターターパック（必須情報）
├── 業種・規模・スタッフ構成
├── 現在の最大ボトルネック（上位3つ）
├── ITリテラシーレベル（1〜5段階）
├── 予算感・決裁者
└── ヒアリングで上村が感じた「空気感」（自由記述）
```

### 柱2：Kai自己検証プロトコル（Anthropic レッドチーム思想の適用）

**Anthropicのやり方：** モデルをリリースする前に、専門チームが意図的に失敗を探す「レッドチーム」を行う。

**アートソウル版：** 成果物を上村に見せる前に、Kai自身が批判者になる。

```
Kai自己検証チェック（提案書の場合）
① Knowledge内に根拠のない数値・主張はないか
② このクライアントが一番懸念しそうな点を3つ挙げよ
③ 競合コンサルがこの提案を見たら何と批判するか
④ 6ヶ月後にこの提案が失敗するとしたら原因は何か
⑤ 上村が修正したくなりそうな箇所を予測して先に修正したか
```

この検証を経た上で「Kai自己検証：済」のスタンプを付けて上村に渡す。
上村の10%レビューは「全部確認する」から「Kaiの自己検証への合意確認」に変わる。

### 柱3：段階的自律権限拡張（Anthropic RSP思想の適用）

**Anthropicのやり方：** モデルの能力が上がるたびに、安全評価を通過しないと次のレベルに進めないポリシー（Responsible Scaling Policy）を運用している。

**アートソウル版：** Kaiの自律権限を4段階で定義し、実績で解放する。

| Level | Kaiの権限 | 解放条件 |
|-------|----------|---------|
| L1（現在）| 全アクションに上村の承認が必要 | — |
| L2 | 提案書ドラフトまで自律実行。上村は最終確認のみ | 連続5件でL1承認率90%以上 |
| L3 | 定型修正・バージョン更新まで自律。公開前のみ確認 | L2で10件・修正指摘3件以下 |
| L4 | 定型案件は公開まで自律。月次で上村がレビュー | L3で6ヶ月・クレームゼロ |

現在L1。L2到達目標：2026年Q3。

### 柱4：フィードバック→ルール化ループ

**問題：** 上村が修正しても、その修正がKaiの次回行動に反映されない（毎回同じ場所を直す）。

**解決策：** 修正が発生したら、その場で原因を分類してルール化する。

```
修正発生時のプロトコル
1. 上村が修正点を伝える
2. Kaiが修正の種類を分類（スタイル/事実/判断/その他）
3. 「これをルール化しますか？」と確認
4. YESなら rules/ に追記。NOなら一時対応として処理
```

これにより `rules/` は上村の好みと判断基準を蓄積した「Kaiの育成記録」になる。

### 柱5：案件パイプライン可視化

**問題：** 案件の状態（ヒアリング中・提案書作成中・公開済み・フォロー中）が会話コンテキストにしか存在しない。

**解決策：** `01_経営管理/` に案件パイプライン管理ファイルを作成。Kaiが更新を担う。

```
01_経営管理/
└── 案件パイプライン.md  ← 全案件の一覧と現在ステータス
```

## 6. 分業マップ（目標状態）

| 領域 | 上村がやること | Kaiがやること |
|------|-------------|-------------|
| 営業・関係構築 | クライアントとの対話・信頼構築 | 提案資料・フォローメール文案の準備 |
| ヒアリング | 現場訪問・感触の把握 | 事前質問リスト・ヒアリング後の整形 |

| 公開・送付 | 承認 | GitHub Pages設定・URL生成 |
| 社内知識 | 判断・方針決定 | 記録・整理・ルール化 |
| コンテンツ | テーマ決定・経験提供 | 執筆・編集・公開準備 |

## 7. 前提と注意事項

- このロードマップは上村の確認・修正を経て初めて有効になる
- Kaiの自律権限拡張は実績ベース。実績なく権限を広げない
- クライアントに実害が出た場合はL1に戻す
- 3ヶ月ごとにKaiが進捗レビューを出し、上村が承認する
