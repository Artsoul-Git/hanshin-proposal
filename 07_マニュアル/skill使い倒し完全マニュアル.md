## 2. シナリオ別スキルレシピ

### 【新規クライアント獲得】

**セミナーで見込み客を集めてクロージングまで持っていく**
```
① /research        → 業界・競合を調査してセミナーテーマを決める
② /course-build    → カリキュラムを設計する（体験セミナー形式）
③ /seminar-slide   → スライドを生成してGitHub Pagesで公開
④ /hearing-sheet   → ヒアリングシートを準備
⑤ /proposal-outline → ヒアリング後すぐに提案骨子を作る
⑥ /sme-ai-proposal → 提案書HTMLを生成
⑦ /publish-proposal → URL発行してクライアントに送付
```

---

**ヒアリングを受けてその日中に提案書を送る**
```
① /hearing-sheet   → 事前にヒアリングシートを作る（当日持参）
② /proposal-outline → ヒアリング後すぐ骨子生成（15分で完成）
③ /sme-ai-proposal → 骨子をインプットに提案書HTML生成
④ /fact-check      → ファクト・法的リスクを確認
⑤ /publish-proposal → URL発行して当日夜に送付
```

---

### 【セミナー・研修の制作】

**0からセミナーを作って集客まで**
```
① /research        → 競合セミナー・受講者ニーズを調査
② /course-build    → カリキュラム設計書を作成
③ /seminar-slide   → スライド+トークスクリプト生成
④ /persona-review  → ターゲット視点で品質確認
⑤ /marketing       → 集客LP・コピーを設計
```

**既存スライドをリニューアルしてトーク台本を作る**
```
① /talk-script     → 既存スライドからトーク台本を生成
② /persona-review  → ペルソナ視点でチェック
③ /seminar-slide   → 必要なら新規スライドとして再構築
```

**研修プログラムを複数回シリーズで設計する**
```
① /course-build    → 全体カリキュラム設計（Section構成）
② /wbs-gantt       → 研修スケジュールをExcelで管理
③ /seminar-slide   → 各回のスライド生成（セクション別）
④ /hr-transform    → 受講者の定着・行動変容を設計
⑤ /kpi-design      → 研修効果の計測KPIを設計
```

---

### 【契約・法務処理】

**新規クライアントと契約を結ぶ**
```
① /nda             → まずNDAを締結
② /biz-contract    → 業務委託契約書を生成（立場：乙有利）
```

**相手から送られてきた契約書を確認する**
```
① /contract-check  → 立場「乙有利」でレビュー
② /doc-compare     → 修正版が来たら前版との差分確認
③ /biz-contract    → 必要なら自社版を対案として提示
```

**見積もりから請求まで**
```
① /billing-docs    → 見積書生成（EST-番号自動採番）
   → 承認後 /billing-docs で請求書生成（AR-番号）
```

---

### 【コンテンツを量産する】

**テーマ1つから複数フォーマットに展開**
```
① /research        → テーマのリサーチと根拠を固める
② /content-burst   → 6種コンテンツを並列生成
   （レポート/ブログ/X/YouTube台本/メルマガ/ビジュアル）
③ /text-refine     → 各コンテンツのトーン・文体を調整
```

**Brain記事（有料コンテンツ）を書く**
```
① /research        → テーマの市場・需要を確認
② /write-brain-article → 参考記事スタイルで執筆
③ /fact-check      → ファクト確認
④ /marketing       → 販売ページのコピーを書く
```

---

### 【戦略を立てる】

**事業の方向性を整理して数字に落とす**
```
① /rashinban       → 目標を入力してマンダラ→ロードマップを生成
② /issue-tree      → 課題を分解してクリティカルイシューを特定
③ /stakeholder     → 関係者の整理と攻略シナリオ設計
④ /profit-plan     → EPDCARサイクルで収益計画を構築
⑤ /finance         → P&L・DCF・損益分岐点で数値検証
```

**AI導入支援の提案を強化する**
```
① /research        → 業界のAI活用事例を調査
② /marketing       → クライアントのUSPを整理
③ /kpi-design      → AI導入効果の計測KPIを設計
④ /hr-transform    → 現場への浸透計画を作る
⑤ /sme-ai-proposal → 上記をすべて反映した提案書を生成
```

---

### 【日々の業務を回す】

**毎日の業務ログを残して月次報告に使う**
```
① /daily-report    → 毎日：音声で話すだけでExcel日報化
② /eval-daily      → 毎日：ロードマップとの整合スコアを確認
③ /eval-weekly     → 毎週：Stop/Scale評価と翌週タスク確認
④ /monthly-report  → 月末：日報データから月次レポートを自動生成
⑤ /eval-monthly    → 月末：総括とロードマップ見直し
```

**プロジェクトのスケジュール管理**
```
① /wbs-gantt       → WBS・ガントチャートをExcelで作成
② /visualize フロー → 業務フローをブラウザ表示HTMLで図解
③ /eval-weekly     → 週次でガントとの差分を評価
```

---

### 【M&A・事業承継】

**買収検討から意向表明まで**
```
① /research        → 対象業界・市場を調査
② /ma              → 企業価値評価（3手法）・DDチェックリスト
③ /finance         → DCF・感応度分析で数値検証
```

## 3. カテゴリ別スキルガイド

### ── コンテンツ制作 ──

#### `/course-build` — カリキュラム設計

**強み：** 受講者が「気づいたらゴールにいる」設計ができる。  
**いつ使うか：** セミナー・研修・オンライン講座を設計するとき。`/seminar-slide`の前工程として使うと最も効果的。  
**コツ：**
- ヒアリングの「ゴール」を「約束できる範囲」に設定させること。できないゴールは書き直す。
- 「現状×障壁×理想」の3軸で受講者を描写させること。受講者の言葉そのままが重要。
- 出力をそのまま `/seminar-slide` に渡せる。引き継ぎメモを必ず出力させること。

```
起動例：
  /course-build
  「AI活用研修のカリキュラムを設計して」
  「中小企業の事務スタッフ向けのChatGPT研修を作りたい」
```

---

#### `/seminar-slide` — セミナースライド一気通貫

**強み：** ヒアリングからGitHub Pages公開まで1コマンドで完結。  
**いつ使うか：** セミナーの当日スライドが必要なとき。体験ワーク付きの構成が自動で設計される。  
**コツ：**
- `course-build` でカリキュラム設計書を先に作ってからここに渡すと品質が上がる。
- ペルソナ情報（現場担当者：経営者の比率）を明確に伝えること。
- 生成後に `/persona-review` を通すと「伝わるか」の検証ができる。

```
起動例：
  /seminar-slide
  「ChatGPT活用セミナーのスライドを作って。60分。経営者向け。」
```

---

#### `/content-burst` — コンテンツ6種並列生成

**強み：** 1回の指示で6フォーマットが同時に出てくる。コンテンツマーケティングの量産に最適。  
**いつ使うか：** ブログ・SNS・動画・メルマガを同テーマで一気に作りたいとき。  
**コツ：**
- テーマは絞ること。「AI活用」より「ChatGPTで議事録を5分で作る方法」のほうが出力が鋭くなる。
- `/research` を先に走らせてエビデンスを固めてから渡すと各コンテンツが事実ベースになる。

---

#### `/deck-sprint` — 資料3点セットを5分で生成

**強み：** 社内報告・MTG資料・クライアントへの中間報告を最短で出せる。  
**いつ使うか：** 明日のMTGに資料が必要なとき。`/seminar-slide` より軽量で速い。  
**コツ：**
- セミナー品質が不要な「報告・共有」用途に使う。凝ったトークスクリプト不要。
- テンプレート差し替え方式なのでトークン消費が少ない。長い会話の中でも使いやすい。

---

### ── 提案・営業 ──

#### `/sme-ai-proposal` — AI導入支援提案書生成

**強み：** Knowledge（ヒアリング記録）があれば、クライアント固有の言葉で提案書が出てくる。  
**いつ使うか：** ヒアリングが終わった後。Knowledge に記録が入っていることが前提。  
**コツ：**
- Knowledgeにない情報は架空になる。ヒアリング後すぐ文字起こしを入れること。
- 「要件定義.md に追加して」が最強。追加情報が来るたびに都度言うだけで提案書の品質が上がり続ける。
- 提案書は v1から始まる。修正はバージョンが自動で上がる。旧版は残る。

---

#### `/hearing-sheet` — ヒアリングシート生成

**強み：** 業種12種×部門4種の組み合わせで最適な設問を自動で作る。  
**いつ使うか：** 初回ヒアリングの前日。当日持参できる状態にしておく。  
**コツ：**
- 訪問前日に「明日○○業の経営者にヒアリングする」で `/hearing-sheet` を起動するだけ。
- ヒアリング後、文字起こしをそのまま渡すと記入済みシートに変換できる。

---

#### `/proposal-outline` — 提案骨子（15分で完成）

**強み：** ヒアリング直後に「どんな提案をするか」の骨子を即出力。長い提案書の前工程として使う。  
**いつ使うか：** ヒアリングが終わってすぐ。その場でスマホに入力して帰り道に骨子を確認できる。  
**コツ：**
- 4タイプ（AI/DX推進型・ITツール導入型・マーケティング型・複合）を自動判定する。
- 骨子をそのまま `/sme-ai-proposal` に引き継げる。

---

### ── 戦略・分析 ──

#### `/rashinban` — 目標→ロードマップHTMLを一発生成

**強み：** 5問答えるだけでマンダラ64項目→4象限マトリクス→フロー図→ガントチャートが全部入った1ページのHTMLができる。  
**いつ使うか：** 「何をすべきかわからない」「優先順位をつけたい」「計画を可視化したい」とき。  
**コツ：**
- 迷ったらまずこれ。全体像が見えたら次のスキルを選べる。
- クライアントへの初回提案書代わりにも使える（URLで共有可能）。

---

#### `/issue-tree` — 問題をロジックツリーで分解

**強み：** 「なんとなく感じる課題」を構造化してクリティカルイシューを特定できる。  
**いつ使うか：** 提案の問いを立てる前、戦略を考える前、会議のアジェンダを作る前。  
**コツ：**
- Why Tree（なぜ？）→ 根本原因特定に使う
- How Tree（どうすれば？）→ 解決策の網羅に使う
- What Tree（何から成る？）→ 概念・要素の分解に使う
- まず `/issue-tree` で問いを立ててから他のスキルを使うと、ゴールがズレない。

---

#### `/visualize` — 4種の図をHTMLで生成

**強み：** draw.io不要。ブラウザで開いてそのまま使える。コピーボタン付き。  
**いつ使うか：** 会議資料・提案書・研修資料に図解が必要なとき。  
**コツ：**
```
/visualize 4象限 [テーマ]   → 2軸で優先度を整理
/visualize マンダラ [テーマ] → 目標を64タスクに展開
/visualize フロー [テーマ]   → 業務フロー・プロセスを図解
/visualize ガント [テーマ]   → 実行タイムラインを設計
/visualize 深掘り [テーマ]  → 4種を段階的に生成（ドリルダウン）
```

---

### ── 財務・法務 ──

#### `/billing-docs` → `/nda` → `/biz-contract` の使い順

クライアントとの取引はこの順番：
```
1. /hearing-sheet  → ヒアリングしてニーズを把握
2. /proposal-outline → 骨子を作って合意
3. /billing-docs   → 見積書を発行（EST-番号）
4. /nda            → NDA締結（個人情報・機密を扱う場合）
5. /biz-contract   → 業務委託契約書を締結
6. 着手・納品
7. /billing-docs   → 請求書を発行（AR-番号）
```

#### `/contract-check` — 相手契約書のチェック

**コツ：**
- 立場は「乙有利」で始める（受託者＝乙が有利な条件を目指す）。
- 高リスク条項は必ず弁護士確認を推奨。Kaiは法律相談ではなくレビューの補助。
- 修正交渉が始まったら `/doc-compare` で前版との差分を毎回確認する。

#### 日次→週次→月次の評価サイクル

```
毎日夕方：
  /eval-daily   → 自動でgit/Tasksを読んでスコアを出す（1分）

週末：
  /eval-weekly  → Stop/Scale評価と翌週タスク候補を出す（5分）
  → 出てきたタスク候補を承認するだけで Kai Tasks に自動登録

月末：
  /eval-monthly → 月次総括とロードマップ見直し提案（15分）
  → ゴールのズレを修正してから翌月の /rashinban に繋げる
```

**コツ：**
- `/eval-daily` は「コスト0」。git を動かしているだけで自動評価される。毎日やらない理由がない。
- `/eval-weekly` の「Stop候補」は感情を排除した客観評価。続けるかどうかの判断材料として使う。
- 月次は `/eval-monthly` 後に `/rashinban` を使ってロードマップを更新する。

## 5. 使い倒しのコツ10選

### ① 「迷ったら `/rashinban`」がデフォルト起動
何をすべきか迷ったとき、まず `/rashinban` に目標を投げる。マンダラとロードマップが出るので、そこから使うスキルが自然に見えてくる。

### ② `/project-intake` は省略してよい
スキルを知っているなら直接コマンドを打つほうが速い。`/project-intake` は「どのスキルを使うかわからないとき」専用。

### ③ Knowledge に入れれば入れるほど提案書が「現場の言葉」になる
ヒアリング後すぐにKnowledgeへ文字起こしを投入すること。次回の提案書生成がまるで違う。

### ④ スキルはチェーンして使う
1コマンドで終わりにせず、出力を次のスキルのインプットにする。`/research → /profit-plan → /finance` の流れが戦略の精度を上げる。

### ⑤ 「要件定義に追加して」が1番コスパが高い
新情報が来るたびにこの一言を言うだけで、要件定義.mdが更新され続ける。次回の提案書はそれを自動で参照する。

### ⑥ 文書系は「立場」を最初に言う
`/biz-contract`・`/contract-check` は「甲有利/乙有利/公平」を最初に明示する。これを省くと微妙な仕上がりになる。

### ⑦ 評価スキルは感情を切り離すために使う
`/eval-weekly` の Stop候補は「やめる理由を理論化してくれる」ツール。感情でズルズル続けているものを整理するのに使う。

### ⑧ ペルソナレビューは提出前の最終防衛
`/persona-review` はターゲットに「刺さらない箇所」を客観的に指摘する。提案書・セミナー・LP など重要成果物は必ず通す。

### ⑨ `/text-refine` は「Kaiへの話しかけ」として使う
完成した文章ではなく、音声のような雑な入力でも `/text-refine` が整えてくれる。「〜やった、〜した、あとこれ確認して」でメールになる。

### ⑩ 月末に「今月何やったか」の棚卸しを `/eval-monthly` に任せる
git履歴・Tasks・セッションログを自動で読むので、自分で振り返らなくていい。出てきた「翌月重点テーマ」をそのまま `/rashinban` に渡すと翌月ロードマップが完成する。

## 6. よくある失敗と回避法

| 失敗パターン | 原因 | 回避法 |
|------------|------|--------|
| 提案書に架空の数字が入る | Knowledgeが空のまま生成した | ヒアリング後すぐKnowledgeに文字起こしを投入する |
| スキルを起動したが何も返ってこない | サーバーが起動していない (kai-tasks等) | `ensure-server` コマンドを先に実行する |
| 契約書のレビューが甘い | 「公平」で依頼した | 自分に不利な条件は「乙有利」で強めに見てもらう |
| セミナーが「説明会」になった | course-build を省いてslide生成した | 必ず `/course-build` でカリキュラム設計してから `/seminar-slide` に渡す |
| 収益計画が楽観的すぎる | profit-planを単独で使った | `/research` で市場を調べ、`/finance` で数値検証してから `/profit-plan` を使う |
| 評価が甘くなる | 自己評価で感情が入る | `/eval-weekly` の自動評価に任せる。Stop候補は素直に受け取る |
| コンテンツが薄い | テーマが抽象的すぎた | `/research` を先に走らせてエビデンスを固める。テーマは「1文で言えるくらい絞る」 |
| 文書の差分が追えない | 手動で比較していた | 修正版が来たら必ず `/doc-compare` に通す |
