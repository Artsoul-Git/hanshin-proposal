3. スキル連携マップ

どのスキルがどのスキルに繋がるか。出力を次のスキルのインプットにするのが使い倒しの鉄則。

【インプット収集フロー】
/hearing-sheet ──→ /proposal-outline ──→ /sme-ai-proposal ──→ /publish-proposal
/research      ──→ /marketing        ──→ /profit-plan
                               ──→ /sme-ai-proposal

【分析・設計フロー】
/rashinban ──→ /issue-tree ──→ /stakeholder ──→ /sme-ai-proposal
                              ──→ /kpi-design
                              ──→ /hr-transform

【コンテンツ制作フロー】
/course-build ──→ /seminar-slide ──→ /persona-review
/research     ──→ /content-burst
              ──→ /write-brain-article

【財務・法務フロー】
/finance           ──→ /profit-plan
/billing-docs（見積） ──→ /nda ──→ /biz-contract ──→ /billing-docs（請求）
/contract-check    ──→ /doc-compare（修正版が来るたびに）

【業務管理フロー】
/daily-report ──→ /monthly-report
/eval-daily   ──→ /eval-weekly ──→ /eval-monthly ──→ /rashinban（翌月ロードマップ）

【品質保証（どこにでも挟める）】
[任意の成果物] ──→ /fact-check
[任意の成果物] ──→ /persona-review
[任意のテキスト] ──→ /text-refine

4. 使い倒しのコツ10選

1「迷ったら /rashinban」がデフォルト起動
何をすべきか迷ったとき、まず /rashinban に目標を投げる。マンダラとロードマップが出るので、そこから使うスキルが自然に見えてくる。
2スキルはチェーンして使う
1コマンドで終わりにせず、出力を次のスキルのインプットにする。/research → /profit-plan → /finance の流れが戦略の精度を段違いに上げる。単体使用と連携使用では品質がまるで違う。
3Knowledge に入れれば入れるほど提案書が「現場の言葉」になる
ヒアリング後すぐに Knowledge フォルダへ文字起こしを投入すること。次回の /sme-ai-proposal がまるで違う。架空数値・推測が入らない。
4「要件定義に追加して」が1番コスパが高い
新情報が来るたびにこの一言を言うだけで要件定義.mdが更新され続ける。次回の提案書はそれを自動で参照する。積み重ねが提案書の深さになる。
5/course-build は /seminar-slide の前工程として使う
/seminar-slide 単体で起動すると「説明スライド」になりがち。/course-build でカリキュラム設計書を先に作り、受講者のゴールと各レクチャーの主張を明確にしてから渡すと、スライドとトークスクリプトの品質が格段に上がる。
6文書系スキルは「立場」を最初に言う
/biz-contract・/contract-check は「甲有利/乙有利/公平」を最初に明示する。省くと微妙な仕上がりになる。受託者として仕事をするなら「乙有利」が基本。
7評価スキルは感情を切り離すために使う
/eval-weekly の Stop候補は「やめる理由を理論化してくれる」ツール。感情でズルズル続けているものを整理するのに使う。出てきた候補は素直に受け取る。
8ペルソナレビューは提出前の最終防衛
/persona-review はターゲットに「刺さらない箇所」を客観的に指摘する。提案書・セミナー・LP など重要成果物は必ず通す。自己評価は甘くなるので客観的な視点が必要。
9/text-refine は「Kaiへの話しかけ」として使う
完成した文章ではなく、音声のような雑な入力でも /text-refine が整えてくれる。「今日○○やった、あとこれ確認して、明日までに返信したい」だけでメールになる。
10月末の「棚卸し」を /eval-monthly に任せる
git履歴・Tasks・セッションログを自動で読むので自分で振り返らなくていい。出てきた「翌月重点テーマ」をそのまま /rashinban に渡すと翌月ロードマップが完成する。

5. よくある失敗と回避法

失敗パターン原因回避法
提案書に架空の数字が入る Knowledgeが空のまま生成した ヒアリング後すぐKnowledgeに文字起こしを投入する
スキルを起動したが何も返ってこない Kai Tasksサーバーが未起動 ensure-server コマンドを先に実行する
契約書のレビューが甘い 「公平」で依頼した 受託者として不利な条件は「乙有利」で強めに見てもらう
セミナーが「説明会」になった /course-build を省いてスライド生成した 必ず /course-build でカリキュラム設計してから /seminar-slide に渡す
収益計画が楽観的すぎる /profit-plan を単独で使った /research で市場を調べ /finance で数値検証してから使う
自己評価が甘くなる 自己評価で感情が入る /eval-weekly の自動評価に任せる。Stop候補は素直に受け取る
コンテンツが薄い テーマが抽象的すぎた /research を先に走らせてエビデンスを固める。テーマは「1文で言えるくらい絞る」
文書の差分が追えない 修正版を手動で比較していた 修正版が来たら必ず /doc-compare に通す
レクチャーのトークが薄くなる 主張だけ決めて説明を省いた /course-build の「主張+4要素（Why/What/How/事例）」を各レクチャーに設計する
M&A評価が甘い /ma だけで完結させた /finance で独立してDCF・感応度分析を実施して数値を二重確認する
⚠ 法的注意事項 /nda・/biz-contract・/contract-check が生成する文書は参考資料であり、法的拘束力のある書類の最終確認は弁護士・司法書士に依頼すること。Kaiはレビューの補助であり法律相談ではない。
