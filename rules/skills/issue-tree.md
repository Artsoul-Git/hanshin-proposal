# /issue-tree スキル

**用途:** 問題・課題をMECEに分解し「本当に解くべきクリティカルイシュー」を特定する。仮説思考と「So What?/Why So?/How?」連鎖で、論理の漏れと優先度を明確化する。

> すべての戦略・提案・計画の「問いの設定」に使う。間違った問いを解いても意味がない。このスキルが全スキルの前処理として最も汎用性が高い。

---

## 発動条件

ユーザーが `/issue-tree` を入力したとき、または以下の依頼があったとき：

- 「問題を整理したい」「本当の課題を特定したい」
- 「何から手をつければいいか」「優先順位をつけたい」
- 「なぜうまくいかないのか原因を掘り下げたい」
- 「提案書を作る前に問題構造を整理したい」
- 「〇〇を増やすにはどうすればいいか」

---

## 2つのツリー方向

| タイプ | 問い | 用途 |
|--------|------|------|
| **Why So?（原因分解）** | 「なぜ問題が起きているのか？」 | 根本原因の特定・課題の優先順位付け |
| **How?（解決分解）** | 「どうすれば目標を達成できるか？」 | 解決策の網羅・打ち手の選定 |

どちらが適切かは入力内容から自動判定する。両方必要な場合は両方作る。

---

## フロー

### STEP 1：問いの設定（最重要）

受け取った問題を「解くべき問い」として正確に定義する。

```
【問いの設定】
曖昧な表現：「売上が上がらない」
↓ 変換
鋭い問い：「なぜ既存顧客からの追加受注が過去6ヶ月で30%減少しているのか？」

ポイント：
- 測定可能（数字・期間が入っている）
- スコープが明確（どの売上か）
- 答えが行動につながる形式
```

問いが曖昧な場合は「この問いで正しいですか？」と確認してから進む。

---

### STEP 2：イシューツリーの展開（MECE）

3〜4階層まで分解する。各階層でMECEチェックを実行する。

```
【イシューツリー出力形式】

問い：「〇〇はなぜ/どうすれば△△なのか？」

├─ 大イシュー①：〇〇
│   ├─ 中イシュー①-1：〇〇
│   │   ├─ 小イシュー①-1-1：〇〇
│   │   └─ 小イシュー①-1-2：〇〇
│   └─ 中イシュー①-2：〇〇
│
├─ 大イシュー②：〇〇
│   ├─ 中イシュー②-1：〇〇
│   └─ 中イシュー②-2：〇〇
│
└─ 大イシュー③：〇〇
    ├─ 中イシュー③-1：〇〇
    └─ 中イシュー③-2：〇〇

MECEチェック：
  漏れ：〇〇の観点が未カバー → [あり/なし]
  ダブり：〇〇と〇〇が重複 → [あり/なし]
```

---

### STEP 3：仮説の設定

各イシューに対して「おそらくこれが原因/解決策だ」という仮説を立てる。仮説を先に立てることで検証すべき情報が絞られる。

```
【仮説リスト】

仮説①：〇〇である（確信度：高/中/低）
  根拠：〇〇
  検証方法：〇〇

仮説②：〇〇である（確信度：高/中/低）
  根拠：〇〇
  検証方法：〇〇
```

---

### STEP 4：クリティカルイシューの特定

以下の2軸で各イシューを評価し、最優先で解くべき問いを1〜2個に絞る。

```
評価軸：
  インパクト：解決したときの効果の大きさ（高/中/低）
  実行可能性：すぐに着手できるか（高/中/低）

【優先度マトリクス】

              実行可能性：高    実行可能性：低
インパクト：高  🔴 最優先        🟡 中期対応
インパクト：低  🟢 早期着手      ⚪ 保留

クリティカルイシュー（最優先）：
  → 「〇〇」（理由：インパクト高・即着手可能）
```

---

### STEP 5：So What?連鎖（示唆の抽出）

クリティカルイシューから「だから何をすべきか」を3段階で引き出す。

```
事実：「〇〇という状態である」
  ↓ So What?（だから何？）
示唆：「つまり〇〇が問題の核心だ」
  ↓ So What?（だから何をすべき？）
行動：「したがって〇〇を最初にやるべきだ」
  ↓ So What?（それで何が変わる？）
成果：「結果として〇〇が達成される」
```

---

### STEP 6：アクション提言

```
【アクション提言】

■ 今すぐやること（1〜2週間）
  1. 〇〇（理由：クリティカルイシューの根拠検証）

■ 次にやること（1〜3ヶ月）
  2. 〇〇

■ やらないと決めること
  ・〇〇（優先度低・リソース分散リスクが高いため）

■ このイシューツリーの限界
  ・〇〇のデータが未確認のため仮説段階
  → `/research` で検証することを推奨
```

---

## 他スキルとの連携

```
/issue-tree（本当の問いを特定）
    ↓ クリティカルイシューが判明
/research（その問いを実データで検証）
    ↓ データ取得
/finance（数字で意思決定）
    ↓ 財務インパクト確認
/marketing（解決策をLP・提案に落とす）
    ↓
/profit-plan（収益計画に組み込む）
    ↓
/sme-ai-proposal（提案書に仕上げる）
```

> **このスキルは他スキルの「前処理」として最も価値を発揮する。**
> 問いが曖昧なまま `/marketing` や `/profit-plan` を動かすと、精度の高い「間違った答え」が出る。
