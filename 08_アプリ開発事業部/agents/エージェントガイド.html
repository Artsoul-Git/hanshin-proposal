1. ARCH — 統括エージェント

🏗
ARCH（アーチ）
アプリ開発事業部 統括AI / 唯一の対外窓口

上村さんと直接対話する唯一のエージェント。「設計士の思想」で動き、実装の前に必ず設計図を引きます。配下7体の専門AIを統括し、案件開始〜納品まで責任を持ちます。

自律実行できること
  • 要件整理・設計ドラフト
  • コーディング・テスト
  • ドキュメント作成
必ずオーナー承認が必要
  • 技術スタックの最終決定
  • 追加費用が発生する提案
  • クライアントへの対外納品

ARCHへの指示の仕方

ARCHは 08_アプリ開発事業部/CLAUDE.md を読み込んで動きます。以下の形式で指示すると正確に動きます。

# 新規案件 まる様向けに出退勤管理システムを作りたい。 GASとAppSheetで、スマホから入力→Sheetsに記録→月次集計が自動で動く仕組み。 # 途中経過の確認 今の開発状況を教えて。何フェーズ目？ # 特定フェーズを指定 SHIELDにテストを依頼して

3. 各エージェント詳細

📋
SPEC（仕様書記）
要件定義・仕様書作成 — 開発の起点
起動タイミング
案件開始時
呼び出し元
ARCH
次のエージェント
WIRE

役割：ヒアリング内容をMUST/WANT/NOTに分類し、チームが迷わず動ける要件定義書を作成します。技術スタック案を3択以内で提示してARCHに判断を仰ぎます。

出力：outputs/<案件名>/spec.md

禁止事項要件を推測で補完して確定させること・工数を楽観的に過小見積もること・NOT要件を曖昧にすること。
🔌
WIRE（設計師）
フロー・画面・DB設計 — 実装前の最後の砦
起動タイミング
SPEC完了後
呼び出し元
ARCH
次のエージェント
実装担当3体

役割：要件定義書をもとに「実装が始められる設計図」を作成します。データフロー・画面設計・DB/シート設計・トリガー設計を4ファイルにまとめます。設計の漏れをここで全部潰すのがWIREの使命です。

出力： wire/flow.md wire/screen.md wire/db.md wire/trigger.md（GAS系のみ）

承認ポイントWIREの設計図完成後、上村さんの承認を得てから実装に進みます。ここが「引き返せる最後のポイント」です。
⚙️
GASBOT（GASビルダー）
GAS / AppSheet / Google Sheets 実装担当
起動タイミング
WIRE完了後
技術スタック
GAS / AppSheet / Sheets
AI連携
Gemini API対応

役割：GAS（Google Apps Script）でバックエンドロジックを実装。AppSheetでUIを構築。「クライアントが自走できるコード」を書くことが設計思想です。

出力： src/<ファイル名>.gs src/シート設計.md src/AppSheet設定手順.md

コーディング原則個人情報マスキング必須（masking.gs）・GAS 6分タイムアウト対策・CONFIG オブジェクトへの設定値集約・エラーハンドリング必須。
🔨
WEBSMITH（HTMLビルダー）
HTML / CSS / JavaScript 実装担当
起動タイミング
WIRE完了後
技術スタック
HTML/CSS/JS
成果物原則
単一HTMLファイル

役割：提案書・セミナー資料・ダッシュボード・インタラクティブレポートなどのHTML系成果物を担当。「ブラウザで開いてそのまま使える」状態を原則とします。

出力：src/<ファイル名>.html

Kaiの設計仕様AS社の提案書HTMLは html { zoom: 1.4; } が標準仕様。SVG内テキストは最小12pxで設定。印刷・PDF対応を@media printで必ず実装します。
🔗
HOOKUP（外部連携師）
LINE bot / Gemini API / Notion / Slack など外部API連携
起動タイミング
WIRE完了後
得意領域
外部API連携
GASとの関係
橋渡し設計担当

役割：LINE bot・Gemini API・Notion API・Slack Webhook等の外部サービス連携を実装します。GASとの橋渡し設計も担当し、「つながる」を確実にします。

出力： src/webhook.gs src/api_client.gs src/設定手順.md

🛡
SHIELD（QAテスター）
テスト・品質保証 — 「動く」から「確実に動く」へ
起動タイミング
実装完了後
合格条件
全項目PASS
不合格時
実装に差し戻し

役割：実装完了後の全テストを担当します。機能テスト・エッジケース・異常系・クライアント環境での動作確認を実施。SHIELDが全PASS出すまでSCRIBEは起動されません。

出力：shield/test-report.md

差し戻しルール1項目でもFAILがあれば実装に差し戻します。「ほぼ動く」での通過は認められません。これがASの品質基準です。
📝
SCRIBE（ドキュメンター）
マニュアル・引継ぎ資料・コードコメント整備
起動タイミング
SHIELD全PASS後
完了定義
一人で運用できる状態
対象読者
クライアント / AS社内

役割：「読んだ人が一人で運用できる状態を作る」のが完了定義。クライアント向け操作マニュアル・AS社内引継ぎメモ・コードコメント整備の3種を作成します。

出力： manual/操作マニュアル.md manual/引継ぎメモ.md コードコメント追記

SCRIBEの品質基準「詳細は担当者まで」というFAQは禁止。「設定方法・接続先URLのない引継ぎメモ」は禁止。技術用語をそのまま使ったクライアント向けマニュアルは禁止。

4. 正しい使い方と注意事項

ARCHへの依頼の書き方

状況良い例悪い例
新規案件「まる様向けに〇〇システムを作りたい。要件は〜」「コード書いて」（要件なし）
設計確認「WIREの設計図を見て、懸念点があれば教えて」「どう思う？」（主語が曖昧）
テスト依頼「SHIELDに〇〇システムのテストを依頼して」「テストして」（案件名なし）

フェーズ飛ばしは危険

よくある失敗「急いでいるからWIREをスキップして実装に入りたい」という要望は、設計ミスが実装後に発覚するリスクを高めます。ARCH は設計フェーズのスキップを提案しません。どうしても急ぐ場合はARCHに「急ぎの理由」を伝え、スコープを絞ることで対応します。

技術スタック選定の原則

  1. クライアントが既に持っているツール（ライモBiz・GWS・Sheetsなど）
  2. 追加コストゼロで実現できるか
  3. クライアントが将来自分で修正・運用できるか
  4. Claude Codeで実装・デバッグ・改修できる構造か

5. 成果物の置き場所ルール

すべての成果物は 08_アプリ開発事業部/outputs/<案件名>/ 以下に保存します。
フォルダ内容担当
outputs/<案件名>/spec.md要件定義書SPEC
outputs/<案件名>/wire/設計図（フロー・画面・DB・トリガー）WIRE
outputs/<案件名>/src/実装ファイル（.gs / .html）GASBOT / WEBSMITH / HOOKUP
outputs/<案件名>/shield/テスト報告書SHIELD
outputs/<案件名>/manual/操作マニュアル・引継ぎメモSCRIBE
納品完了の定義受託案件：① 動作するコード/アプリがoutputsに存在 ② SHIELDの全項目PASS ③ SCRIBEのマニュアルがクライアントに渡せる状態 ④ 「クライアントが一人で使い始められる」状態
